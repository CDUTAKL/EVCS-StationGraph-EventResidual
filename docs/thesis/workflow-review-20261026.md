## 评分应怎样改

后续正式评价应先给“当前稿的绝对质量”，再解释“相较上一稿改变了什么”。不能把维持或提高旧分作为目标。量表仍固定为12项、原始90分，不能因重新盲评临时提高门槛或改变权重。

建议下一次评分协议升级采用以下顺序：

1. 冻结当前稿、同一证据白名单、量表与锚点。初始评分包不包含历史分数、旧评语、修订投入、目标分数或“已改好”等评价性说明。
2. 三个隔离上下文只评当前稿，逐组件从零给分；分别保存原始报告、已读范围和未核验事项。技术、创新、可读性是关注侧重，不能使用不同标准。
3. 独立核查评语中的事实，再裁定总分。报告与正文冲突时以核实证据为准；本轮关于[76]“未比较”的错误指控就是需要这道门槛的例子。
4. 先冻结当前绝对分，再另做前后稿差异审查。差异审查说明新增贡献、已消除疑点和未变限制，不把相邻半分视为精确测量。
5. 公开分项、理由、分歧和置信限制。AI上下文隔离能减少锚定，不能保证绝对公正；同一模型的视角仍可能相关。

现行2.0正式发布器要求配对记录。本轮按该协议完成三隔离视角及配对校准，不能把它事后改称“仅当前稿从零盲评”。上述当前稿先行的发布模式需要独立升级协议和校验器后再启用，权重不变。本次未暗中更换评分制度。

对讨论记录中评分建议再补三条：盲评包需要足够的事实证据，不能只给论文文本而仍宣称核验了复现性；多视角中位数和范围可用于描述分歧，不能覆盖已经核实的评语事实错误；文字结构、术语和近邻比较的实质改善也可提高对应项，不能把“没有新训练”直接等同于评分漂移。同稿同证据下的分差应先记录为判断波动，核查后再解释原因。

日常小修只更新问题台账与确定性核验，不例行发布新总分。正式评分放在内容冻结、关键证据补齐或用户明确要求时进行。分数可以升、降或不变；不能用“修订过”推导“必须更高”。

## 文件保留与空间

- 正式入口为outputs/thesis中同题名的一个DOCX和一个PDF，历史通过Git LFS恢复。
- 普通任务只使用一个临时候选目录；只有用户要求或明确交付里程碑才另存命名版本。
- 缓存保留哈希、检查结果和必要页面；重型全页渲染只保留当前候选。最终全页视觉验收仍按现有要求执行。
- 本次历史迁移保留一份完整Git bundle和SHA映射；迁移副本在源仓库同步并验证后清理。这是历史恢复保护，不是日常每轮新增的备份。
- 对此前已经存在的版本文件，先列大小、证据引用和保留原因，再清理；不能按文件日期批量删除仍承担审计来源的旧稿。

沿用outputs/thesis的两个正式路径，不再另建deliverables/current或每里程碑复制一套releases目录。里程碑优先用Git标签指向既有提交。日常保留一个活动候选入口；确需保留的失败候选单列原因和期限，不能把“最近3份或7天”解释成无限累积。LFS按正式稿和大型文件的明确路径登记，小型结果图PDF继续按现有方法管理。

冻结分析包在仓库内约1.6 MB，原始输入留在仓库之外；外部261 MB可携带包是明确的迁移交付，不应每个任务再复制。不同CSV若对应不同统计口径，仍是必要复算材料；“最小交付”按论证和复算依赖确定，不强制所有项目只保留一图一表。

## 已补的轻量入口

复用现有thesis_release.py，新增两个只读子命令，create/verify门槛保持原样：

```bash
python3 scripts/thesis_release.py inventory --output docs/thesis/artifact-inventory --dry-run
python3 scripts/thesis_release.py resolve outputs/thesis/基于站内多关系图与机制诊断的充电节点短期负荷预测研究_正式论文.pdf --ref HEAD
```

inventory只生成路径、哈希、大小、角色、Git/LFS状态及保守引用提示；不删除、移动或复制文档。resolve验证指针与本地内容哈希后返回只读LFS对象路径，供PDF对比等工具直接读取；不再另存一份基线PDF。旧提交可显式传入commit-map.csv，输出同时保留原请求ID和迁移后的查找ID。对象路径只能读取，不得交给编辑器原位保存。

日常检查复用现有prepare/collect、哈希缓存及影响索引，不再新建平行的verify_fast/verify_full流程。“完整门”要求覆盖完整，不等于每次无条件重新计算576项；代码、数据、标签或统计口径变化时重算受影响的依赖闭包。最终全页视觉验收不能由影响索引代替。

旧任务scope_violation需要明确接受、拒绝或拆分后的关闭记录，历史错误不能清零后伪装通过。工作树存在本地资料时，应使用隔离工作树或已登记的基线，不能通过git clean删除资料来追求形式上的干净。当前外部图件写任务结束后，才进行正式文件的集中导出和交付。

终审推送前须再次核对共享源工作区的稿件与图件输入SHA，并确认写任务结束。独立副本干净只说明该副本内部一致，不能代替原工作区的冻结确认。任务锁和仪表盘可以加强该规则，但手动绕过受管入口的修改仍需靠发布前差异检查发现。

“每日推送”改为小而完整的任务验收后及时提交、推送；不自动发布未复核内容。回滚依据可以是已验证bundle、明确提交SHA和保留引用，标签提供便捷入口；当前最终里程碑标签等图件联合验收后再建立。

## 值得封装的重复工作

优先增强现有入口：让任务结束时自动完成回收、哈希核对、影响索引、一次候选导出和保留清单。避免再增加一套蓝图、评分或论文流程。第二优先是正式文件发布入口：校验通过后替换两个稳定文件、核对LFS指针、提交Git并按保留清单回收本任务临时目录。盲审仍需实际阅读和法证判断，不能包装成确定性的自动加分程序。
