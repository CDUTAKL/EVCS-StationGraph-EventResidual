**坑 1：`soffice` 抛 `DeploymentException`。** 症状是转换直接失败、无任何 PDF 产出。原因是默认用户配置档损坏或被占用。解**不要杀进程**（会误伤用户开着的 LibreOffice），改用独立 profile：`soffice --headless -env:UserInstallation=file:///tmp/lo_profile_thesis ...`。

**坑 3（最严重）：LibreOffice 默认导出把图压成 300 DPI JPEG。** 默认参数导出的 PDF 只有 9.6 MB，而官方件是 170 MB。`pdfimages -list` 显示官方件图片为 1199–2013 PPI、无损；默认导出被降到 **300 PPI、JPEG 有损**。这会直接让“图像有效 PPI”交付门槛不合格。正确参数：

```
--convert-to 'pdf:writer_pdf_Export:{"UseLosslessCompression":{"type":"boolean","value":"true"},"ReduceImageResolution":{"type":"boolean","value":"false"},"Quality":{"type":"long","value":"100"}}'
```

改用该参数后 PDF 为 169 MB、最大 2013 PPI、129 页，与官方件同档。

**另一条重要提醒**：构建脚本的 `--cover-source` 默认读取**现有官方 DOCX** 取封面字段。所以必须**先构建、后覆盖官方件**，顺序反了封面会丢。

## 4. 盲审历史与合规性：为什么“多少分”是个陷阱

### 4.1 分数序列（仅内部记录）

本项目从 11-01 到 11-09 共跑过多轮盲审，分数序列如下：

> 80 → 81 → 83 → 85 → 87（带锚定） → 73/78（首次隔离） → 74/75（第二轮） → 76/76.5（第三轮） → 80.5/73.5（最终隔离轮）

**这条序列本身就是本项目最重要的一个发现。** 前四轮分数一路走高到 87，但一旦改为“隔离评审”（评审看不到历史分数、看不到既往评审报告），分数立刻掉回 73–78。这不是论文变差了，而是**前四轮的上升是锚定假象**——评审被告知“上一轮 83，看看这次改进”，于是它就在 83 附近打分。

`AGENTS.md` 里对此有明确记录：“轮次披露了前一次分数所产生的上升序列，在评审读同一份手稿且完全无历史时无法复现。上升序列是披露的产物，不是改进的证据。”

### 4.2 11-09 12:20 那轮的合规问题

用户当轮的要求是“跑四个独立盲审老师”，获得 80 / 74 / 71 / 70 四个分数，随后交接笔记写成“平均 73.75、最不利 70、C 档”。

按项目自己的协议 `EVCS-BLIND-REVIEW-1.2`，这轮**不能作为论文成绩**，原因有二：

1. **人数不合规**：协议要求 **2 位**独立评审。4 位既不是 2 位，也不是协议允许的“第三位仅用于分歧复核、无效报告替换或补充视角”。
2. **合成方式不合规**：协议明确“不取均值或中位数，不将 AI 分数换算为学校 A/B/C/D，不预测真实评审结果”。而交接笔记做了“取均值 73.75”与“最不利 70 → C 档”两次转换。

11-06 那轮（3 位：A 80.7 / B 81.4 / C 74.4）同样不是 2 位。11-09 01:32 那轮（R1 80.5 / R2 73.5）**是**合规的 2 位隔离评审，其最不利 73.5 才是当前唯一可引用的正式读数。

### 4.3 结论：把分数当缺陷清单用，不要当成绩用

这不是文字游戏，它直接决定你该做什么。如果相信“73.75 是成绩”，那么所有精力都会投在“怎么把分数推上去”，而历史已经证明这条路在本项目走过四次、全部失效（80→81→83→85→87 之后隔离即回落）。如果把它当缺陷清单，那么真正该做的是：逐条核实每个缺陷是否真实、能否修复、修复的代价与收益。

本轮（11-09 下午）走的就是第二条路：不追分数，只修可核实的缺陷。结果是有 5 项实质缺陷被修复（见第 3 节），而分数完全未测。

### 4.4 一条必须传给下一任的纪律

**任何未来的盲审 prompt 都不得包含历史分数、不得包含“上一轮多少分、这次改了什么”这类框架、不得让评审打开 `docs/thesis/scoring/history.json`、`publication-status.json`、既往评审报告或修订清单。** 这是隔离性的硬要求，写进了 `AGENTS.md`，违反它得到的分数一律无效。

## 13. 工程陷阱清单（本项目实际踩过的，逐条记录）

这一节是十天内真实发生过的事故与误区。每一条都花了时间，请直接复用结论，不要重新踩。

### 13.1 数据与指标类

**陷阱一：零值被导出成极小正数，掩码全错。** 本项目遇到两次。第一次是 RA-Hurdle 的 1e-17 污染，把 61% 的零键算进非零分母，让非零 MAE 从真实量级变成 0.0533，凭空造出“−80.6% 改善”。第二次是 2026-11-09 主结果重放，零值变成 1e-11～1e-7，让我按“活跃节点 ≥3”筛选时得到 70,856 个实例而不是 13,536。**防御方法：任何新导出的 npz，第一步先数“精确零的个数”，与归档件对比；不一致就不得用于任何掩码类指标。**

**陷阱二：跨协议拼接区间。** 摘要原先写“事件层覆盖仅 1.9%–3.87%”。但 1.9% 来自回溯协议的标准共形、3.87% 来自事件时刻协议的冻结逐节点，中间还漏了同一个表里的 5.92%（冻结行为分层）与 3.9%（规则路由分层）。**把两个不同协议的最小值拼成区间**，既跨了协议又漏了路径。修正后为 1.9%–5.92% 并逐路径点明。

**陷阱三：把学习曲线差当成性能增量。** 摘要曾写“同轮次比较下节点门控的调参 MAE 仍低 21.6%–43.4%”，但那其实是第 10/20/30 轮的**学习曲线差**；收敛后的真实增量是 2.69%–3.08%（60 轮）、3.08%/2.89%（120 轮）。这是评审 P1 点名的错误，已改。

**陷阱四：指标陷阱——小样本子集上排序假象。** 整站基线在“全部实例”上 top-3 全中率反而高于主模型（0.3845 对 0.2589），因为 80.9% 的实例活跃节点 ≤2，top-3 由并列零值的稳定排序决定，常数次序偶然命中。**只在 ≥3 活跃的 13,536 个实例上比较才有意义**，那里趋势完全反转。任何排序类指标都必须先检查分组内的并列结构。

### 13.2 构建与渲染类

**陷阱五：`aligned` 嵌套 `cases` 会让 LaTeX→OMML 转换器崩溃**，渲染成一整行乱码。修法是拆成多行 `aligned`、把 `cases` 的定义移入正文文字。同类：`\left[` 配 `\!` 也会出错。**每次改公式后必须重建并目检渲染结果**，不能只看源码。

**陷阱六：`soffice` 的 `DeploymentException`。** 默认配置档损坏或被占用时，转换直接失败且无输出。**不要杀进程**（用户可能正开着 LibreOffice/WPS），用 `-env:UserInstallation=file:///tmp/lo_profile_thesis` 走独立 profile。

**陷阱七：默认 PDF 导出把图压成 300 DPI JPEG。** 这是最隐蔽的一个：导出“成功”、页数正确、能打开，但图片质量已不合格。判据是**文件体积**——官方件 170 MB，默认导出只有 9.6 MB，差 17 倍。必须用无损参数（见 3.10）。

**陷阱八：`make_toc_map.py` 依赖“页码是页面最后一行”。** 正文页排满时该假定失效。必须用 `pdftotext -layout`。

**陷阱九：等宽列让长标签表格崩坏。** 生成器 `widths = [Cm(14.66/cols)]*cols`，7 列时每列 2.09 cm。长标签表必然折行成 5–6 行，并把整表推走造成半空页。**新增表格前先按列数估算每列宽度**；列多时优先考虑转置而不是加列。

**陷阱十：`--cover-source` 默认读现有官方 DOCX。** 所以必须“先构建、后覆盖官方件”。顺序反了封面字段会丢。

### 13.3 流程与验证类

**陷阱十一：只看文本回滚、不看代码回滚。** 11-09 上午的残差化（0.015704）在正文层被撤销了，但代码里的 `load_lag1` 第 8 通道与 `pred = base + delta` 一直留着，直到 11-09 下午才发现。**验收必须同时看文档与代码**；判断“代码是否回到某个数值的版本”最硬的证据是 `git diff <commit>^ -- <file>` 输出为空、且 blob 哈希相同。

**陷阱十二：目录里的提交不等于干净提交。** 中途另一个会话做了一次 `git commit`，必须先检查它提交了什么（`git show --stat HEAD`），确认没有把你在编的状态一起提交。这次幸好只有 5 个 npz 和 1 个脚本。

**陷阱十三：粗阈值检测器会漏掉真问题。** “字符数 < 200”的空白页检测漏掉了填充率 0.285 的半空页（因为它有 350 个字符）。正确做法是**用文字包围盒算纵向填充率**，并剔除页眉页脚。

**陷阱十四：自己的校验脚本也会错。** 本轮我写的 TOC 校验把印刷页码又减了一次偏移，得出 132/132 全错的荒谬结论；改用直接比对后是 131/132 正确，剩下那 1 条还是我做子串匹配的假阳性。**当校验结果反常（全对或全错）时，先怀疑校验器本身。**

**陷阱十五：不要为迎合指令而破坏证据。** 图脚本的 `pad_inches` 修复，执行代理实测发现“历史统一值 0.10”只对部分图成立（`fig5_4` 实为 0.05），于是拒绝统一值、改为逐图取值并附磁盘尺寸依据。这是正确做法。**当指令与实测冲突时，报告冲突并给出证据，不要静默迁就指令。**

### 13.4 关于“自我披露”的一条经验

本项目花了很多轮讨论“要不要删掉不利披露”。实际测量后的事实是：编辑性自贬措辞（不显著 / 证否 / 未能 / 劣势 / 自证）**已经是 0**，“仍低于”只剩 3 处、“瓶颈”3 处、“仅低”1 处。可删的部分早就删完了。

真正卡住的两处是**结构性**的：一处在表 3-1（AGCRN 更优是表格的状态，不是文字的表述），一处在 13 处散布的零值层拆解（它支撑着“分层能力”这个贡献声明）。把它们删净，得到的不是高分论文，而是**无支撑的过度声称**——而过度声称在盲审里比自我披露更容易被击穿，也更难在答辩时挽回。

反过来，Kimi 那份 84 分意见里明确把“没有回避负面结果”列为**优点**，原话是“这些表述不会天然扣分，反而增强了结果的可信度”。所以“删披露必然涨分”这个判断，本项目内部的证据并不支持。
