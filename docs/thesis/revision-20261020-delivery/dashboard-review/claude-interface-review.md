## 结论

接口已具备可用的第一版闭环：蓝图准备、启动 Claude Code、写回进程状态、接收状态栏遥测、自动回收工作区差异，再交由 Codex复核。它确实能够证明“本机启动过 Claude Code 进程并收到过状态栏回调”，也能把任务状态、允许路径、变更路径、退出码和用量字段放在一个本机只读页面上查看。

第一轮试用的主要价值是**发现并阻止误验收**：LANGUAGE-003 的稿件改动在授权范围内，但同一准备基线之后 `scripts/thesis_blueprint_dashboard.py` 也发生变化，因此回收器把任务标成 `scope_violation`，没有把它误报成正常待复核。当前状态记录同时显示 Claude PID 已结束、退出码为 0、回收已完成，验收仍为 `pending_codex_review`。这是正确的交接状态。

目前不能把这次 `scope_violation` 归因成 Claude 擅自修改了文件。回收器检测的是共享工作区相对基线的变化，不能判断具体由哪个进程或参与者写入。当前界面也只显示“范围外变化数量”，没有解释这是“检测到并发工作区变化”还是“执行者违反范围”。因此首轮试用证明了**检测能力**，但也暴露了必须尽快完善的**隔离与归因表达**。

## 主要判断

### 1. Claude 是否真的启动：可验证到“本机 CLI 子进程”，不能验证到服务商侧

启动器先确认交互终端和 `claude` 可执行文件，再通过 `subprocess.Popen` 启动 CLI，并将返回的子进程 PID 写入 `state.json`；等待进程退出后记录退出码和结束时间，随后自动调用 `collect`（`scripts/thesis_blueprint.py:1250-1308`）。本次记录有 PID、时间、退出码、模型字符串和状态栏快照，足以判断 Claude Code CLI 确实运行过，不是只准备了任务包。

PID 检查使用 `os.kill(pid, 0)`，只能说明该编号当前对应一个可见进程；不能校验它仍是原来的 Claude 进程。PID 复用、进程身份替换等极端情况下可能误判；状态栏快照与 `execution-report.json` 也由本地任务进程提供，不是服务商签名凭据。因此面板适合回答“CLI 是否启动、是否仍在运行、是否返回”，不应把它写成服务商账单或远端模型执行证明。

### 2. 状态栏新鲜度和退出判定：逻辑谨慎，表达基本准确

仅当任务状态为 `executing`、PID 当前存在且状态栏快照不超过 60 秒时，才显示 `telemetry_live`。过期、未来时间戳和未知时间都不会显示实时；任务还停留在 `executing` 但 PID 不存在时，界面显示进程已退出、等待状态收尾。这避免了“页面五秒刷新就等于遥测实时”的误解。

有两个小边界：一是 `kill(pid, 0)` 没有绑定进程名或进程启动时间；二是 statusline 异常捕获的兜底文字目前写“Claude Code进程状态正常”，但状态栏异常本身并不能证明进程状态，建议改成“Claude Code状态栏遥测暂不可用”，避免把遥测失败说成进程正常（`scripts/thesis_blueprint_statusline.py:157-170`）。

### 3. Token、费用与额度：边界处理诚实，不应承诺账户余额

状态栏适配器只保留白名单字段：上下文输入/输出 token、当前用量、缓存 token、上下文占用率、客户端估算费用、持续时长，以及输入中实际包含的有限 rate-limit 项；原始输入、路径、会话标识和未知字段会被丢弃，临时文件权限设为目录 `0700`、文件 `0600`（`scripts/thesis_blueprint_statusline.py:57-124`）。界面明确把费用叫“客户端估算”，token 不等于账户累计用量；DeepSeek 会话未给出配额时显示不可用，而不是从 token 推算额度。LANGUAGE-003 实际投影为 provider/account quota 均不可用，符合现有证据。

当前实现有一项显示上的优先级风险：只要临时目录中存在本任务 ID 的 statusline 文件，即便它已过期或没有有效数值，`task_projection` 仍用它整体覆盖执行报告里的数值遥测（`scripts/thesis_blueprint_dashboard.py:370-378`）。因此，某些任务可能有最终报告用量，却只看到空白或陈旧状态栏字段。建议将“最后状态栏快照”和“最终执行报告用量”分开展示，或至少在状态栏没有字段时回退显示报告用量，并标明各自来源/更新时间。

### 4. 蓝图任务不是操作系统沙箱：回收是审计，不是强制边界

蓝图会冻结精选证据摘录、允许路径和任务前工作区基线；回收器对授权路径计算哈希，对既有范围外脏文件用大小/修改时间指纹，并把新变化、提交变化和保护包变更列入回收报告。`CLAUDE.md` 和蓝图 README 也明确写出：`allowed_paths` 是审计约束，不是 OS 级文件边界；Claude 原生文件工具仍处于项目工作区；Git 忽略文件可能无法被 `collect` 发现；不要在共享工作树同时运行两个写任务。

LANGUAGE-003 正好验证了这个限制：它在一个共享 checkout 中准备并执行，之后另一项并行工作改变了仪表盘脚本；收集器正确拒绝将工作标为干净。但它无法把改动归因给 Claude，也无法让两项任务互不干扰。对并行编辑，优先改用独立 Git worktree；若必须共用 checkout，就串行执行并在启动前后明确冻结/回收。未来可为任务增加工作区锁或独立执行目录，并在报告里把“执行者超范围改动”和“基线后外部/并发改动”分开描述。

另一个精度边界是范围外文件的基线通常没有内容哈希，只有大小与修改时间；仅触碰文件时间戳也可能被判为变化，而当前回收报告不能仅凭该指纹证明内容确实不同。对分类有争议的范围外文件，应由 Codex 用 Git diff 或显式哈希复核，不能只凭 dashboard 徽标认定责任。

### 5. 第一轮的可用性与稳定性

用任务选择器、状态卡片、允许/变更路径、执行时刻、遥测和复核状态组合，足以让作者回答几个关键问题：Claude 是否被启动、现在是否仍活着、报告是否已回收、是否超出蓝图范围、token/额度哪些可见。当前三条本机 GET 均成功，且实际任务状态和本地 JSON 一致；合成边界场景也未把过期快照当作实时。整体可作为日常协作接口的第一版使用。

当前验证尚未覆盖：锁屏/浏览器重启、服务重启、端口冲突后的操作指引、长时间运行时浏览器错误恢复，以及真实运行中的连续 statusline 更新。页面接口通过只读 HTTP 检查，但本次未做完整截图式浏览器视觉验收。因此稳定性结论限定为“本地服务与数据投影正常”，不等同于全面 UI/系统稳定性验收。
